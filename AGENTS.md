## What this is

A personal Android home-screen widget app for the owner's Samsung S24 Ultra (One UI, Android 14+), sideloaded via adb, never published.
It shows commute ETA with live traffic and a route map (Google Maps Platform), calendar-event routing, leave-by advisors, and several on-device routine automations.
Single user, single device; there is no backward-compatibility audience beyond the owner's own installed build and stored data.

## Behavioral model (as approved by the owner)

- Window model: `commuteDays` plus a To Work window (default 7:00-10:00) and To Home window (default 17:00-20:00) drive everything; outside a window (and on non-commute days) the widget is calendar mode, and inside a window it runs the same calendar pipeline for event selection (event takeover, plain card for an unlocated or far event) rather than auto-fetching the commute route or map, but when no event pre-empts and the snapshot is `CALENDAR_EMPTY`, the card body shows the in-window commute body instead of the calendar view - the window label (`To Work` or `To Home`), the morning brief when events exist today, and the sleep caption, with no `Next up` line and no wind-down block - below which the commute pill row (Leave by, Best, Ride, in that order) flows left to right and wraps onto further rows when the card width fills, computed from an estimated pill width since Glance has no flow layout; the route and map render only after a Ride tap.
- Calendar mode shows the next event remaining today (query extends past midnight by `eventTakeoverMinutes` so imminent after-midnight events still route).
- Located events starting within `eventTakeoverMinutes` (default 120, the unified nearness threshold) route from current location with a map, while farther located events and unlocated events render a full-width plain card at zero Google API cost.
- A calendar-event location containing a virtual-meeting URL or platform marker (`http://`/`https://`, `teams.microsoft`, `zoom.us`, `meet.google`, `webex`, or the literal 'Microsoft Teams Meeting') is normalized to unlocated at the calendar reader, before it can win the located-over-unlocated preference or enter the routed pipeline.
- A failed device location fix for a located event (Location switched off, or no fix within the 15-second timeout) is not a routing failure: `eventRouteOrigin` substitutes the saved Home place as the origin, so the map, ETA, and leave-by still render, describing the trip from Home rather than from wherever the phone actually is.
- A first-attempt (new-target) event-routing failure of any remaining cause (geocode, Routes, Static Maps) falls back to the plain name+time card instead of a broken routed shell (0-min ETA, warning glyph, calendar-emoji map placeholder); a same-target failure (an event that already routed successfully) is unchanged and still shows stale route/map data with the warning glyph.
- An `event_near` one-shot WorkManager wake flips a far located event to routed when it enters the nearness window.
- When no events remain today, the widget renders the wind-down card: a `Next up` section listing the next two calendar events from tomorrow onward within seven days, each as its title plus a day-and-time line (`Tomorrow 9:32 pm`, `Thu 10:00 am`), with the alarm line underneath; the commute window itself is never advertised on this card.
- Event takeover: a located event starting within `eventTakeoverMinutes` (default 120) replaces the commute view even inside windows.
- Tap-to-ride lifecycle: `RideState` (phase OFFERED, RIDING, INTERRUPTED, REACHED, plus `routed` set true after the ride's first successful fetch, keyed by local date and direction) drives the Ride pill, the routed map, and the Reached pill; a Ride tap that changes the stored ride state writes phase RIDING and runs a `bypassCooldown = true` TAP refresh to run Routes and Static Maps and render the map (`SnapshotMode.COMMUTE`) - a repeat tap that does not change the stored state is a normal TAP refresh subject to the 5-second debounce, so it cannot spend a second Routes call - a first ride routes the fixed Home-to-Work or Work-to-Home trip, a resumed ride (tapped again from INTERRUPTED) sets `fromCurrentLocation = true` so every riding refresh routes from `currentDeviceLocation` instead, capped at a 5-second fix (well inside the roughly 10-second Glance action budget) and falling back to the fixed window origin on timeout or failure (mirrors `eventRouteOrigin`'s Home fallback), an event takeover while riding wins and flips the phase to INTERRUPTED, and a Reached tap (same changed-state gate) writes phase REACHED, consumes the ride for that window today, and returns the card with Leave and Best hidden until the next window - REACHED nulls the probe leave-by (`probeLeaveByMinute`), the commute-surface snapshot leave-by (`shouldShowLeaveBy`, event snapshots keep theirs), and the Best line (`shouldShowBestDeparture`), and the stale date-plus-direction key makes the next slot resolve back to OFFERED with the pills returning.
- Window probe and ride failure: once per window per local date, on the first in-window refresh whose ride phase is OFFERED and only when leave-by is enabled, one Routes call for the fixed window trip (no Static Maps, no snapshot write) stores a `CommuteProbe`, drives the card's Leave pill, and arms the existing precise leave-by alarm through the existing shared helpers, with a failed probe storing nothing and retrying on the next in-window refresh and never failing the calendar refresh that follows; a ride fetch failure keys the first-attempt-versus-same-target split on `RideState.routed` rather than on the previous snapshot (`isRideFirstAttempt` is true whenever the matching ride state has phase RIDING and `!routed`), so a first-attempt failure reverts the phase (RIDING to OFFERED, or to INTERRUPTED for a resumed ride), sets `lastRideFailed = true`, and runs the calendar pipeline so the card returns with the Ride pill tinted the leave-by late color, while a same-target failure while already riding keeps the existing stale-map-plus-warning-glyph behavior with the phase staying RIDING; `shouldOfferRide` also re-offers the Ride pill when the phase is RIDING, the snapshot is still `CALENDAR_EMPTY`, and no refresh is in flight, so a fetch that died mid-flight (cancelled past the Glance action budget, or thrown) leaves a tappable pill instead of stranding the card with no ride control.
- Leave-by advisors: commute (arrive-by targets, live-traffic based, precise one-shot alarm notification) and event (predicted traffic beyond `eventRealtimeThresholdMinutes`, buffer `eventLeaveByBufferMinutes`, one notification per event).
- Best departure: samples predicted traffic at 30-minute steps across the CURRENT commute window (morning = home to work, evening = work to home, auto-switching), once per window per day, shown as a "Best: h:mm" pill in the card's commute pill row and as a map pill on the map corner; hidden while a calendar event is displayed, hidden on the map (though not the card) while a ride is active, since Reached takes that map-pill slot and best-departure stops being actionable once riding, and hidden everywhere once the ride is REACHED, until the next window's date-plus-direction stops matching the consumed state.
- Refresh triggers: TAP (user, including the Ride and Reached pill taps, which pass `bypassCooldown = true` to `refreshNow` only when the tap actually changed the stored ride state - an unchanged repeat tap is a normal TAP refresh subject to the 5-second debounce and cannot spend a second Routes call - so a state-changing tap inside the debounce window cannot strand the widget with the pill gone and no map), AUTO (window boundaries, calendar changes), TICK (20-minute event-freshness tick, event-driven chain with zero idle wakeups).
- A WorkManager content-URI observer on the calendar provider refreshes within about a minute of any calendar change.
- Routine automations (all on-device): wind-down card (next two upcoming calendar events with day-and-time labels + next clock-app alarm), countdown captions ("in 1h 45m" / "Free for 2h 10m"), morning brief ("3 meetings - first 10:00 am"), alarm line on the empty card.
- Widget appearance: owner-configurable background opacity (One UI translucency), text scale, and map-pill corner; ETA is traffic-colored (green/amber/red) with a traffic dot; pending renders as 45 percent alpha of the accent; stale (over 10 minutes) renders grey.
- Health layer (v6): six core features (sleep estimation from UsageStats KEYGUARD_SHOWN/KEYGUARD_HIDDEN events with screen-event fallback only for zero-keyguard-event nights and 14-day rolling history as nudge input only, evening walk advisor with window-gated pill visibility, water reminders with Health Connect hydration writes and meeting suppression, supplement routines, audiobook commute detection via MediaSession with installed-app picker, Health Connect 1.1.0 for steps/exercise) plus nine experimental toggles default OFF under **Experimental nudges** (sleep-debt brief soften, gym-day protein priority, restless-night focus shield, post-Audible walk latch, daylight walk preference, focus gap chip, post-gym water pulse, morning-light line, caffeine-cutoff line).
- Sleep tap pills: while the sleep-estimate toggle is enabled, `To bed` (bed glyph, 21:00-02:00) and `Woke up` (sunrise glyph, 04:30-10:00) record persistent timestamps and anchor the automatic keyguard estimate; the tap itself is a cheap bounded write (timestamp + snapshot strip + re-render) and the full local recompute runs on an immediately scheduled `health_boundary` run, keeping heavy reads off the roughly 10-second Glance action budget - no network, no notifications.
- Health suppression hierarchy: audiobook playback suppresses ALL health nudges; restless-night shield suppresses water and walk until first event ends or 10:00; water is suppressed only while a calendar meeting is ongoing (owner reversed the prior commute-map ban 2026-08-31 - water now competes by priority like any other pill); maps retain max two health pills, while calendar-empty and wind-down cards show up to four built-in health pills and four custom reminder pills per row with `+N` overflow; 2x2 renders zero health UI; health elements never inherit pending alpha or stale grey.
- Custom pill reminders (v7): up to six user-defined, widget-only reminders with up to four selected weekday slots each (configured with two-row Mo-Th/Fr-Su day chips to prevent overflow); their shared active window defaults to 60 minutes and is configurable from 15-240 minutes; an active occurrence carries over at 60 percent alpha until dismissed, midnight, or the next non-dismissed slot for that pill; taps dismiss only that `pillId:slotMinute` occurrence locally with no notification or network work; a "Reset dismissed reminders" action in the Reminders screen clears today's `customPillTakenSlots` only, preserving all other day state.
- Settings use an Android-Settings-style nine-category home menu with live summaries: Commute setup, Places & Maps, Alerts & timing, Calendar, Flights, Reminders, Health, Widget appearance, and Access & app info; all permission grants are centralized in Access & app info while feature screens retain status links and automatic prompts.
- Airport mode (2026-09-11): Gmail-added flight events in the selected calendars are parsed by `calendar/FlightParser.kt`; from `airportPillLeadMinutes` before departure the widget routes to the departure airport with Leave by, Best and a To Airport pill, then shows a boarding-pass style flight card (status from AirLabs when `flightStatusApiKey` is set) with Done, and the calendar card previews the next flight as a tappable row only once it is today's headline event, departs within 8 hours, or has its airport window open (`selectPreviewFlight`); `engine/AirportLogic.kt` and `schedule/AirportBoundaryWorker.kt` own the phases and wakeups.
- Flights toggle (2026-10-05): Settings > Flights holds `flightsEnabled` (default on), the two airport lead times (moved from Calendar) and the AirLabs key (moved from Places & Maps); off, `performRefresh` reads no flights at all (the single gate: no takeover, the stored flight preview clears, the airport boundary chain cancels in `AirportBoundaryScheduler.ensureScheduled` and in the refresh's re-arm, and a flight is just another calendar event), the toggle runs a cooldown-bypassing AUTO refresh so a flight card or row leaves the widget at once, and the widget also hides the flight row, flight card and airport pill overlays at render time (`airportSurface`) as defense in depth.
- Wind-down card height budget (2026-10-05): the calendar card's body column is weighted, so Glance gives it exactly the height left under the health footer and the launcher clips anything past it; `windDownLayout` picks the richest "Next up" section that fits (two events with two-line titles and the alarm line, then one-line titles, then no alarm line, then one event; floor one event with a one-line title) from the matched breakpoint height, `calendarCardFooterHeightDp`, `flightPreviewHeightDp` and `LINE_HEIGHT_PER_SP` (1.3 dp per sp, measured on the phone's One UI Sans).
- Two today-only dismissal resets exist: Reminders resets custom pill dismissals; Alerts & timing resets built-in health and experimental nudge dismissals (supplements, walk, sleep pill, morning light, focus gaps) while preserving water taps (they mirror Health Connect hydration writes), `walkNotified` (one notification per day), and detection state.
- "Recalculate last night's sleep" (Alerts & timing > Today) clears only the current morning's stored sleep fields (steps preserved), un-dismisses the sleep pill, and recomputes - the unfreeze path for a value written by an older estimator.

## Hard-won invariants (violating these reintroduces shipped bugs)

- Glance renders at most ten children per container: the calendar card body keeps every block (sleep caption, flight row, "Next up" section, event or none-text block, pill row) as ONE child of the body column, with the section's lines nested in their own Column; the 2026-10-05 "Can't show content" widget was the body passing ten once a flight row joined the sleep caption, two events and the alarm line.
- The "Next up" section never renders more than `windDownLayout` returns for the matched breakpoint height; the time line under a title is never the thing that gets clipped.
- `atMinuteOfDay` in `HealthBoundaryWorker.kt` rolls a minute-of-day past 1439 into the next day; a window end at midnight (a 23:30 water slot's 30-minute active window ends at minute 1440) crashed the process with hour 24 on 2026-10-02.
- Flights off means `performRefresh` reads no flights; nothing downstream (preview, takeover, boundary chain, status fetch) gets its own toggle check, so the gate cannot drift.
- The flight row never names a flight just because it is the next one in the 45-day read: `selectPreviewFlight` requires today's headline event, departure within 8 hours, or an open airport window, or a flight weeks out sits under every card again.

- WorkManager: a worker rescheduling its own unique name must use APPEND_OR_REPLACE; REPLACE from inside a running worker cancels itself. REPLACE is correct only from external callers (ensureScheduled).
- Coroutine cleanup that must run on cancellation (clearing the refreshing flag, final widget render) must be wrapped in `withContext(NonCancellable)`; Glance action coroutines are cancelled after roughly 10 seconds and a cancelled coroutine cannot suspend.
- Notification post-then-mark must go through a shared mutex-guarded helper; separate check-then-act paths double-notify.
- CommuteSnapshot changes must be additive with defaults, and every addition needs a backward-compat decode test against a hardcoded old-format JSON string.
- Cross-package refactors follow deprecate-then-delete: keep old symbols compiling as inert @Deprecated stubs until every consumer is updated, then a final pass deletes them.
- Failure snapshots must not leak fields across mode/target transitions (same-target failures preserve stale data; target changes build clean snapshots).
- The engine's mutex serializes refreshes; the 5-second cooldown skip must not touch the refreshing flag except the deliberate 250ms tap-feedback flash.
- Any new background fetching beyond taps, window boundaries, and the accepted tick is a cost decision the owner must approve explicitly; it is never a silent default.
- Glance renders exactly two static compositions (pending, settled); no animation, no shimmer, no looping.
- ensureScheduled cancels legacy unique work names (v2 fixed refreshes, v4 slot chain) as device-migration hygiene; keep those cancellations.
- Health computation must never fail a route refresh: `computeHealthFieldsSafely` wraps `computeHealthState` in runCatching and carries previous health fields on exception.
- Failure snapshots must carry through `healthNudges`, `sleepEstimateMinutes`, and `shortSleepDay` from the previous snapshot (same-target failures preserve stale health data).
- Health tap actions are idempotent local writes with `NonCancellable` + `updateAll` and never trigger network; water tap records only on confirmed Health Connect write (write failure keeps the pill).
- Restless-night shield is applied at computation time; the widget render path always passes `shieldActive = false` to avoid double suppression.
- `HealthDayState`/`HealthHistory` additions follow the same additive-with-decode-test rule as `CommuteSnapshot`.
- Custom pill occurrences are fully resolved at computation time but stored UNCAPPED; the render layer re-filters against the live taken set for dismissal (never for suppression) and only then applies the surface-specific cap (four on calendar-empty cards, three on maps) and derives the `+N` overflow - capping before the dismissal filter strands stale or lone overflow indicators after taps.
- The boundary chain gate is `healthBoundaryNeeded` (health toggles OR any custom pill), not `anyHealthFeatureEnabled` alone; a pills-only configuration must keep the chain armed, while `health_morning` stays health-toggle-gated.
- Every non-route health rewrite of the snapshot goes through `withHealthComputation`; hand-copying health fields in a worker is how custom pill fields silently went missing once.
- Custom pill day-state and snapshot additions follow the same additive-with-decode-test rule as `CommuteSnapshot`.
- A sleep estimate defers until an end exists and freezes only at 10:00 or on a valid Woke Up tap; the once-per-day write guard is gone, and recomputation remains live until that freeze.
- To Bed and Woke Up taps narrow the strict keyguard search domain and never replace keyguard pairing; only anchored nights may bypass the three-hour plausibility floor.
- The legacy screen-event estimator is fallback-only for a night with zero keyguard events; keyguard data with no qualifying interval is an honest no-estimate result.
- Ride and Reached taps must pass `bypassCooldown = true` to `refreshNow` only when the tap changed the stored ride state; the pre-fetch render already hid the tapped pill, so a cooldown-skipped refresh on a state-changing tap would strand the widget with no pill and no map, while an unchanged repeat tap stays a normal debounced TAP refresh.
- The window probe must never fail the calendar refresh that follows it: rethrow `CancellationException`, swallow every other exception (mirrors `computeHealthFieldsSafely`'s runCatching shape for health).
- `performCalendarRefresh` must cancel the commute leave-by alarm only when the caller resolved true calendar mode (`WidgetMode.Calendar`); an in-window calendar refresh (pre-ride render, event takeover) must not cancel it, or the probe's alarm dies while still inside the window.
- Ride state is keyed by local date and direction and is never cleared explicitly; a stored value from another day or the other window's direction resolves to OFFERED and is otherwise inert.
- `shouldOfferRide` requires `SnapshotMode.CALENDAR_EMPTY`, so the Ride pill can never appear on a `CALENDAR_EVENT` (routed event map) surface, and also re-offers the pill when the phase is RIDING with a `CALENDAR_EMPTY` snapshot and no refresh in flight, so a fetch that died mid-flight leaves a tappable pill instead of stranding the card with no ride control.
- The first-attempt versus same-target ride failure split keys on `RideState.routed`, never on the previous snapshot alone.
- The in-window card body and pill row are width-gated at 220 dp exactly like the health rows, so 2x2 never changes.
- `RideState` and `CommuteProbe` follow the same additive-with-decode-test rule as `CommuteSnapshot`.
- The wind-down card is driven by `CommuteSnapshot.upcomingEvents` only; `nextWindowLabel`, `nextWindowStartMinuteOfDay`, `tomorrowEventTitle`, and `tomorrowEventStartEpochMillis` are decode-only legacy fields that nothing may populate or render.

## Known edges (flagged, accepted, not bugs)

- Cross-midnight leave-by times compare minute-of-day within one day, so the late-red state can be wrong for after-midnight events.
- A TICK refresh that fails on transient network ends the tick chain until the next tap or boundary (deliberate zero-idle-wakeup design).
- A buffer larger than the realtime threshold silently downgrades the event probe to live traffic (arithmetic stays correct).
- Some launchers flatten background alpha to opaque; One UI renders it correctly.
- Event leave-by notifications are computed when routing occurs within `eventTakeoverMinutes`, so an event needing more lead time than the takeover threshold notifies late.
- The junk-location marker list is conservative: a location that is neither a URL, a known marker, nor a trailing bare-integer parenthesized suffix (a bare conference-room code with no capacity number, say) still attempts routing once and lands on the plain card via the event failure fallback after spending the geocode/Routes calls.
- A same-target event failure whose previous snapshot never actually routed (duration 0, no map) now falls back to the plain card on the very next retry instead of preserving the broken shell, so a never-geocodable event (an Outlook room resource, an address Google cannot find) converges within one failed refresh rather than staying broken forever.
- A located event routed while the device fix failed shows the trip from Home; when the owner is elsewhere with Location off, that ETA and leave-by are wrong for where the phone actually is, and the widget gives no visual hint.
- The first-attempt event failure fallback erases the failure reason (`lastErrorMessage = null`), so a plain card caused by a geocode, Routes, or Static Maps failure is indistinguishable from an unlocated event on the widget and in the stored snapshot; diagnosis needs the geocode cache and the `fetchedAtEpochMillis = 0` signature.
- A window whose probe never succeeded and whose ride was then interrupted has phase INTERRUPTED, and the probe requires phase OFFERED, so it does not retry for the rest of that window; no Leave pill or alarm until the next window.
- If the window-end boundary refresh is delayed by WorkManager, a recompose after the window end drops the Reached pill while the stale map lingers until the boundary refresh flips to the card.
- The first ride keeps the fixed origin even when the owner is not at Home or Work; the owner chose resumed-rides-only for device-location routing.
- After a Reached tap, a transient frame shows the stale map with no commute pills (REACHED suppresses Leave by and Best) while the local refresh runs.
- A transient ride-fetch failure leaves the Ride pill red until the next tap or the next window, because nothing clears `lastRideFailed` on connectivity return.
- The pill row wrap is computed from an estimated width (6 dp per character at 12 sp Medium, plus padding), so an unusually wide glyph set could still let one row run slightly long.
- After a process kill mid-fetch with the ride phase RIDING, the refreshing flag stays set in DataStore, and because Glance recomposes on data change rather than on a timer, the re-offered Ride pill appears at the next recompose (a card tap, a DataStore write, a boundary refresh) rather than exactly at the 60-second staleness mark.
- A recovery tap on a re-offered Ride pill within 5 seconds of the died fetch's completion is a normal TAP subject to the debounce, so it plays only the 250 ms pending flash; the next tap fetches.
- The `Next up` day label is a short weekday, unambiguous only because the lookahead is seven days.
- A calendar with fewer than two eligible events in the next seven days shows fewer entries in the `Next up` section.
- The `Next up` section is title plus time only, so a located event listed there is not routed until it becomes today's next event.
- The wind-down height budget is an estimate (1.3 dp per sp, chip rows at 48 dp) against the matched breakpoint, not the physical box: on the owner's 216 dp two-row box with one pill row the section shows both events with one-line titles and the alarm line, with two pill rows one event and no alarm line, and a title that would fit on one line of the real 406 dp width is still budgeted at its `maxLines`.
- TWO_ROW_BREAKPOINT (220x210) matches only while the launcher reports the two-row box at 210 dp or taller; a smaller display-size setting drops the card back to the WIDE composition, whose 110 dp budget always renders the one-event floor.
- With Flights off, a stored AIRPORT snapshot is replaced by the toggle's own refresh; if that refresh returns early (no API key or places), the layouts render the stale airport route as a plain routed map without airport pills until the next refresh.
- After local midnight, an un-refreshed wind-down snapshot's `Tomorrow 9:32 pm` entry is relabelled with its weekday at the next recompose because the label is computed at render time against the stored start, and there is no "Today" case; the next refresh replaces the list.

## API cost profile

- One key, three APIs: Routes (Pro SKU, 5000 free calls per month - the binding constraint), Static Maps and Geocoding (10000 free each).
- Typical day: about 4 boundary refreshes (window-start boundaries no longer spend a Routes or Static Maps call, since the window probe replaced them), about 2 window probe Routes calls (one per window, leave-by enabled), 1 Routes plus 1 Static Maps per ride, the event tick while a routed event shows, up to about 14 best-departure sampling calls; net Routes count is roughly unchanged from before, with fewer Static Maps calls; comfortably inside free tiers.
- Per-minute quota caps are set low in the Google Cloud console as the abuse guard; per-day caps do not exist for these APIs.
